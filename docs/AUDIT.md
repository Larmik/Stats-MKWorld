## 1. Bloquant & sécurité

- [~] 🟠 **A2 — Règles de sécurité Firebase RTDB.** Volet applicatif fait (Firebase Anonymous Auth : `FirebaseRepository.signInAnonymously()`, re-tentée par `MainViewModel`). **Reste hors-repo (console Firebase)** : activer *Anonymous* et durcir les règles RTDB (`auth != null`, idéalement scopé par équipe). Tant que les règles restent ouvertes, l'auth anonyme ne protège rien. *Prévention : rule 40 (secrets & données côté client).* **Suivi : #129.**
- [ ] 🟠 **A4 — Secret OAuth Discord embarqué dans l'APK.** `BuildConfig.DISCORD_API_SECRET` sert au `Credentials.basic(...)` de l'échange de code et de la révocation ([DiscordDataSource.kt:36,52](../app/src/main/java/fr/harmoniamk/statsmkworld/datasource/network/DiscordDataSource.kt)). Sorti du dépôt (`local.properties`), mais un `BuildConfig` se lit par décompilation : le secret est extractable de tout APK publié. → Déplacer l'échange `code → token` côté serveur (Cloud Function), puis faire tourner le secret. *Prévention : rule 40.* **Suivi : #126.**
- [ ] 🟡 **A5 — Sauvegarde Android non filtrée.** `android:allowBackup="true"` avec des règles d'exemple vides (`res/xml/backup_rules.xml`, `data_extraction_rules.xml`) : le token Discord (`access_token`, [DataStoreRepository.kt:78](../app/src/main/java/fr/harmoniamk/statsmkworld/repository/DataStoreRepository.kt)), les DataStore proto et la base Room partent en sauvegarde cloud et se restaurent sur un autre appareil. → Exclure les DataStore/token (ou `allowBackup=false`, les données étant re-synchronisables). *Prévention : rule 40.* **Suivi : #128.**

## 2. Bugs & correctness

- [ ] 🟠 **B27 — Synchro des wars : seule la dernière roster hôte est conservée.** `FetchUseCase.fetchWars(teamId)` fait `clearWars()` (vide **toute** la table, [WarDao.kt:20](../app/src/main/java/fr/harmoniamk/statsmkworld/database/dao/WarDao.kt)) puis écrit les wars d'**une** roster ([FetchUseCase.kt:164-167](../app/src/main/java/fr/harmoniamk/statsmkworld/usecase/FetchUseCase.kt)). Or les 4 appelants l'invoquent **en boucle par roster mkworld** ([FetchUseCase.kt:72](../app/src/main/java/fr/harmoniamk/statsmkworld/usecase/FetchUseCase.kt), [PlayerProfileViewModel.kt:239](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/playerProfile/PlayerProfileViewModel.kt), [SignupViewModel.kt:136](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/signup/SignupViewModel.kt), [DebugViewModel.kt:115](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/debug/DebugViewModel.kt)) : une équipe hôte à ≥ 2 rosters ne garde que les wars de la dernière. → Sortir le `clearWars()` de `fetchWars` (un seul clear avant la boucle, ou clear + écriture de toutes les rosters en une passe). *Prévention : rule 30 (écriture destructive hors boucle).* **Suivi : #104.**
- [ ] 🟡 **B28 — Demande de permission de notification : chemin du repository mort, dépendance à l'`Activity`.** `MainApplication` implémente `ActivityLifecycleCallbacks` sans jamais appeler `registerActivityLifecycleCallbacks(this)` ([MainApplication.kt:14-60](../app/src/main/java/fr/harmoniamk/statsmkworld/application/MainApplication.kt)) → `currentActivity` toujours `null` → dans `NotificationRepository.requestAuthorization()`, `permissionCheck()` renvoie `Denied` : la branche qui lance le launcher et appelle `setNotifAlreadyRequested()` ([NotificationRepository.kt:50-54,60](../app/src/main/java/fr/harmoniamk/statsmkworld/repository/NotificationRepository.kt)) n'est **jamais** exécutée. La demande fonctionne quand même par un autre chemin : `requestAuthorization()` retombe sur `areNotificationsEnabled.not()` → `true`, le VM émet `showNotif`, et **`SignupScreen` ([SignupScreen.kt:59-64](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/signup/SignupScreen.kt)) et `PlayerProfileScreen` ([PlayerProfileScreen.kt:116-134](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/playerProfile/PlayerProfileScreen.kt)) lancent déjà `notificationPermissionLauncher`**. Conséquences : code mort dans le repository, flag `notifAlreadyRequested` jamais posé, et une couche données qui dépend d'une `Activity`. → Supprimer la branche Activity du repository (garder l'état de permission) et garder la demande côté UI. *Prévention : rule 30 (pas de dépendance Activity/UI dans un repository).* **Suivi : #114.**
- [ ] 🟠 **B29 — Écran « mise à jour requise » masqué par le splash (à confirmer sur device).** `setKeepOnScreenCondition { true }` n'est relâché que dans la branche `startDestination` ([MainActivity.kt:45,54-80](../app/src/main/java/fr/harmoniamk/statsmkworld/activity/MainActivity.kt)) ; la branche `needUpdate` pose le `MKDialog` sans libérer le splash → l'app reste figée sur le splash. → Relâcher le splash dans les deux branches. *Prévention : checklist anti-audit (toutes les branches d'un état terminal).* **Suivi : #116.**
- [ ] 🟡 **B30 — Recherche de joueurs : résultats concurrents.** Chaque frappe (≥ 3 caractères) lance un nouveau `viewModelScope.launch` qui parcourt **toutes les pages** MKCentral, sans annuler la recherche précédente ni debounce ([RegistryViewModel.kt:46-61](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/registry/RegistryViewModel.kt), [TeamProfileViewModel.kt:88-105](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/teamProfile/TeamProfileViewModel.kt)) : une réponse lente d'un terme ancien peut écraser le résultat du terme courant, et la rafale d'appels expose au throttle MKCentral. Au passage, `TeamProfileViewModel` n'écarte les alliés déjà présents qu'**à partir de la page 2** (la page 1 est ajoutée sans filtre, L96 vs L100). → `MutableStateFlow` du terme + `debounce` + `flatMapLatest` (ou `Job` annulé). *Prévention : rule 20 (recherche à la saisie).* **Suivi : #118.**
- [~] 🟡 **B31 — `withTrackStats` : mode 12/24 partagé entre wars.** La `var` capturée a disparu (#90 : agrégat mutualisé dans `trackStatsOf`), mais le **comportement** est conservé à l'identique pour rester iso-résultat : `is24p` = mode de la **dernière** war filtrée, appliqué à toutes les manches ([ListExtension.kt:214-224](../app/src/main/java/fr/harmoniamk/statsmkworld/extension/ListExtension.kt), idem `maps` de `withFullStats` L127-131). Latent (les appelants filtrent un seul mode aujourd'hui), faux dès qu'une liste mixte arrive. → Porter le mode par manche dans `trackStatsOf` (comme `warIs24p` dans `withFullStats`). *Prévention : rule 60.* **Suivi : #120.**
- [~] 🟡 **B32 — Génération du Tab classique : adversaire perdu.** (Crash `toInt()` corrigé en #105 : saisie mutualisée en `toIntOrNull() ?: 0`.) Reste : `war.teamOpponent.mapNotNull { getTeam(...) }` efface un adversaire non résolu → `teamWin`/`teamLose` `null` dans le PDF ([EditTabViewModel.kt:149](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/editTab/EditTabViewModel.kt)). → `War.opponentTeams` (repli dégradé, rule 12), comme le tab HLorenzi. *Prévention : rule 12.* **Suivi : #122.**
- [ ] 🟢 **B33 — Id `"null"` passé à la synchro des alliés.** `fetchAllies(team?.id.toString())` envoie la chaîne `"null"` si l'équipe n'a pas été récupérée ([FetchUseCase.kt:69](../app/src/main/java/fr/harmoniamk/statsmkworld/usecase/FetchUseCase.kt), [PlayerProfileViewModel.kt:232](../app/src/main/java/fr/harmoniamk/statsmkworld/screen/playerProfile/PlayerProfileViewModel.kt)). → `team?.let { … }`. *Prévention : rule 60.* **Suivi : #124.**
- [ ] 🟡 **B34 — Positions moyennes hors podiums encore reconverties depuis une moyenne de points.** `Stats.averagePlayerPosition` ([Stats.kt:27-29](../app/src/main/java/fr/harmoniamk/statsmkworld/model/local/Stats.kt), tuile « Pos. moy. » de l'Accueil) et `MapStats.playerPosition` ([Stats.kt:419](../app/src/main/java/fr/harmoniamk/statsmkworld/model/local/Stats.kt), « Position joueur » de la fiche circuit) font `(Σ points / n).pointsToPosition()` : une moyenne tronquée hors barème (11, 13, 14 pts) affiche **« 0 »**, et les manches non courues par le joueur comptent pour 0 pt (`averageForMaps` de `withFullStats`, `playerScoreList` de `MapStats` : `null.positionToPoints()` = 0) → moyenne diluée. - [ ] 🟡 **B35 — Stats circuits 24p : moyennes non corrigées par #102.** Dans `trackStatsOf` ([ListExtension.kt:233-260](../app/src/main/java/fr/harmoniamk/statsmkworld/extension/ListExtension.kt)), (a) le `teamScore` d'une course avec intermission (2 index, 24p) est une **somme** et non une moyenne par manche (onglet Circuits des Classements en 24p, tri par score faussé) ; (b) en vue joueur 24p, toutes les manches des wars du joueur sont agrégées, y compris celles qu'il n'a pas courues (`totalPlayed`, winrate, `playerScore` dilués). - [ ] 🟢 **B37 — Lecture des wars Firebase non tolérante à un id non numérique.** `Map.toWar()` convertit `this["id"].toString().toLong()` ([FirebaseRepository.kt:265](../app/src/main/java/fr/harmoniamk/statsmkworld/repository/FirebaseRepository.kt)) : un nœud `wars/{rosterId}/…` à id absent ou corrompu lève une `NumberFormatException` qui fait échouer **toute** la lecture `getWars` (synchro, diagnostics, migration des wars officielles #156) au lieu d'ignorer l'entrée. → `toLongOrNull()` et `mapNotNull` sur l'entrée invalide. - [~] 🟢 **B11 — Adversaires multi-rosters historiques restés en `teamId`.** Création de war en `rosterId`, affichage/classements par roster et migration RTDB des équipes mono-roster faits. **Limite assumée** : les wars historiques contre une équipe multi-rosters restent en `teamId` (roster joué inconnu) → un item de classement « niveau équipe » subsiste à côté des rosters. ## 9. Matrice audit ↔ prévention

Chaque catégorie d'entrée est rattachée à la cause qui la produit et à ce qui l'empêche de revenir (rules : chemins relatifs à `.claude/rules/`, index dans `.claude/rules-index.md`). |---|---|---|
| Secrets / données sensibles côté client (A2, A4, A5) | Secret placé dans `BuildConfig`, sauvegarde par défaut | `build/release-securite.md` § secrets ; `settings.json` (deny lecture des secrets) |
